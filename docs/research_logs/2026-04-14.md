## Step 22 diagnostic dashboard refactor & test suite

### What changed

#### `pipeline/steps/step22_build_county_diagnostics.py`

**Three-layer architecture refactor** (continuation from previous session — changes were lost in a merge and re-implemented):

- Added `CountyData` dataclass consolidating the 39 loose parameters that were previously threaded through `_dashboard_html()`. Typed fields cover identity, shared context, chart images, data dicts, co-opt results, and step18 data.
- Added pure card-builder functions replacing the old `_append_*` mutating functions:
  - `_coopt_best_of_card`, `_coopt_gallery_card`, `_coopt_detail_cards`
  - `_key_metrics_card`, `_energy_flows_card`, `_rate_plan_card`

- Added `_collect_county_data(...)` to separate data collection from rendering.
- Added `create_executive_summary_card(scenario, county_slug, npv_details, assets_info, statewide_savings) -> str` — a pure function producing a self-contained HTML summary card with:
  - Verdict (Cost-saving / Near break-even / Higher cost) based on `annual_savings > 200` and `annual_savings > -200`
  - Simple payback period (`net_capex / annual_savings`), with "Never" when savings ≤ 0 and "N/A" when capex is missing

  - Solar kW and battery kWh sizing from `assets_info`
  - Statewide percentile rank context (shown only when county is in the dict and n ≥ 3)
  - Fallback chain: `all_electrification` fields → `solar_storage` when any field is None
- Slimmed the `process()` loop to: `data = _collect_county_data(...)` → `html = build_dashboard(data)` → write file.
- Added `statewide_savings = compute_statewide_savings_distribution(...)` before the per-county loop.
- Resolved a merge conflict between upstream fat-loop version (39-param `_dashboard_html`) and the stashed thin-loop version — took the thin-loop version.

**Bug fixed — ordinal suffix for percentile ≥ 21:**

The original suffix logic used string literals in the dict:
```python
# Buggy: for pct=21, returns "1st" (just the suffix, not "21st")
pct_label = f"{pct}th" if 4 <= pct <= 20 else {1: "1st", 2: "2nd", 3: "3rd"}.get(pct % 10, f"{pct}th")
```

Fixed to embed the full number in the f-string:
```python
pct_label = f"{pct}th" if 4 <= pct <= 20 else {1: f"{pct}st", 2: f"{pct}nd", 3: f"{pct}rd"}.get(pct % 10, f"{pct}th")
```

This affects all percentiles whose units digit is 1, 2, or 3 and whose value is > 20 (i.e., 21st, 22nd, 23rd, 31st, 32nd, 33rd, 41st, …, 91st, 92nd, 93rd). The 11th–13th special case is correctly handled by the `4 <= pct <= 20` guard.

### Why

The monolithic `_dashboard_html` function with ~39 parameters was difficult to test, extend, and reason about. The three-layer refactor (data collection → section builders → assembly) makes each layer independently testable and keeps the per-county loop thin. The executive summary card gives end-users a single-glance view of the key economics before diving into the full diagnostic detail.
